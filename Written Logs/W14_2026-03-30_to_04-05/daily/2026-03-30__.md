## Novelty Position (Frozen Draft, Method-Level)

This thesis does not claim novelty from attaching a generic full-scene re-ID module to a standard MOT stack. The novelty claimed in this block is an ambiguity-aware target continuity policy for control: maintain sticky target memory, detect explicit ambiguity windows, delay target switching with a grace window, and propagate ambiguity into control validity handling. This policy is implemented and evaluated inside the existing ROS2 pipeline with latency bounds, timing observability, and explainable failure behavior on edge hardware. Lightweight target-specific appearance memory is treated as the next step under study, not a prerequisite for the current operational contribution.

## Design Rationale Note (Half-Page Draft)

Full-scene appearance matching is not the first choice in this phase because it adds model/runtime complexity exactly where the current system is most constrained: real-time control continuity on embedded hardware. In this stack, the control value comes from stable target identity under ambiguity and short occlusion, not from maximizing generic MOT benchmark score. A full-scene embedding pipeline raises immediate risks in compute variance (`track_ms` jitter), integration scope (feature extraction path, backend API expansion, new failure modes), and explainability during field validation.

A selective target-specific direction is better aligned with thesis constraints. First, the system already has deterministic memory at target-selection level (`prev_id` stickiness), which creates a natural insertion point for ambiguity-aware policies without architecture rewrite. Second, ambiguity and occlusion are already reproducible in existing replay launches, allowing method validation with controlled stress scenarios and measurable pass/fail gates. Third, the control loop can consume target-validity semantics directly, which ties perception-side uncertainty to safety behavior instead of hiding it inside opaque association logic.

Therefore, the near-term method contribution is to formalize and evaluate ambiguity-aware continuity and control-validity handling in the current pipeline. Appearance is still relevant, but as a lightweight, target-specific augmentation after the control-facing baseline is hardened and measured.

## Minimal Ablation Plan (3 Experiments)

1. Tracker backend sensitivity under identical replay
	 - Setup: run `eval_replay.launch.py` with `tracker:=sort`, `tracker:=ocsort`, `tracker:=bytetrack` on same raw bag.
	 - Metrics: target continuity (switch count), dropout duration, `track_ms` median/p95.
	 - Pass criteria: selected backend improves continuity vs SORT without >20% median `track_ms` increase.

2. Ambiguity stress (crossing scenario)
	 - Setup: run `eval_replay_ambiguous.launch.py` with fixed ambiguity window.
	 - Metrics: wrong-target lock duration, switch frequency inside window, post-window recovery time.
	 - Pass criteria: target lock recovers within <=2 seconds after ambiguity window in >=90% runs.

3. Occlusion stress (periodic blackout)
	 - Setup: run `eval_replay_occluded.launch.py` with fixed `period_s` and `drop_s`.
	 - Metrics: re-acquisition delay, continuity degradation, timing stability (`/timing_tracker`).
	 - Pass criteria: no unstable oscillation and bounded re-acquisition delay trend across repeats.
